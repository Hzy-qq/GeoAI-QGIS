问题1:
outputs/chroma/这个文件夹在运行build_chroma_store.py这个脚本之后会有新的文件夹,但是里面是空的,只有chroma.sqlite3这个,用记事本打开里面有些是乱码,这是什么情况?

答案:
这是正常情况，不是构建失败。

`outputs/chroma/` 是 Chroma 的持久化向量数据库目录。运行 `build_chroma_store.py` 后，Chroma 会把 collection、文档、metadata、embedding 向量等内容保存到本地数据库中。

你看到的：

```text
outputs/chroma/chroma.sqlite3
```

就是 Chroma 的核心数据库文件。它本质上是 SQLite 数据库，不是普通文本文件，所以用记事本打开会看到乱码或很多不可读字符。这和 `.gpkg` 文件类似，GeoPackage 也是 SQLite 格式，用记事本打开也不会是正常文本。

也就是说：

```text
chroma.sqlite3 = Chroma 保存向量库数据的数据库文件
```

里面大致存了这些内容：

```text
collection 信息
文档 id
文档 text
metadata
embedding 向量
索引相关信息
```

不要用记事本查看它。判断 Chroma 是否构建成功，应该看脚本输出，例如：

```text
Chroma vector store built:
{
  "path": ".../outputs/chroma",
  "collection": "geoai_knowledge",
  "embedding_model": "BAAI/bge-small-zh-v1.5",
  "documents": 16
}
```

或者运行：

```powershell
python scripts/retrieve_chroma_knowledge.py "计算点要素周围1公里范围内的道路长度"
```

如果能返回相关文档，说明 Chroma 向量库已经正常工作。

总结一句话：
`outputs/chroma/` 不是给人直接阅读的文本文件夹，而是 Chroma 给程序读取的数据库目录；`chroma.sqlite3` 出现乱码是正常的。


问题2:
evaluate_chroma_rag_planner.py这个脚本运行后,后两个case是不支持的,但是还是显示7/7pass,这是pass指的是7个案例都看过了,并不表示7个案例全是正确的,是这个意思么?

答案:
你的理解接近，但需要再精确一点：

`7/7 passed` 不是说“7 个任务全都是支持任务”，而是说“7 个 eval case 的判断结果都符合预期”。

在 `evals/eval_cases.json` 中，前 5 个 case 是支持任务：

```text
road_length_500m_cn
road_length_1000m_cn
road_length_2km_cn
road_length_1_5km
road_length_default_distance
```

它们的预期是：

```json
"expected_supported": true
```

所以这些 case 的 PASS 条件是：

```text
模型判断 supported=true
距离 distance_meters 正确
工具链是 buffer -> clip -> sum_line_lengths
workflow schema 合法
```

后 2 个 case 是不支持任务：

```text
unsupported_building_count
unsupported_school_count
```

它们的预期是：

```json
"expected_supported": false
```

所以这两个 case 的 PASS 条件反而是：

```text
模型正确判断 supported=false
```

也就是说，如果用户问“统计建筑物数量”，当前项目不支持这个任务。模型应该拒绝生成 QGIS 工作流，而是返回：

```json
{
  "supported": false,
  "distance_meters": 0,
  "workflow": {
    "workflow": "unsupported",
    "steps": []
  },
  "reason": "..."
}
```

只要模型这么判断，就是正确的，因此显示 PASS。

所以：

```text
7/7 passed
```

准确含义是：

```text
7 个测试案例中，模型输出都和 expected_supported / expected_distance_meters / expected_tools 等预期一致。
```

不是表示：

```text
7 个任务都被项目支持。
```

面试时可以这样说：

“Eval 不只是测试模型能不能生成支持任务的 workflow，也测试模型能不能正确拒绝不支持的任务。unsupported case 通过，说明模型没有乱编工具或乱生成 workflow，这对 Agent 安全性很重要。”


问题3:
llm_planner.py和chroma_rag_planner.py这两个脚本的运行顺序是谁在前谁在后,其中plan_workflow_with_llm(user_query, extra_context=context)和plan_workflow_with_chroma_rag这两个函数是什么关系呢?

答案:
运行顺序是：

```text
chroma_rag_planner.py 先作为外层入口
  -> 先调用 Chroma 检索
  -> 再调用 llm_planner.py 中的 plan_workflow_with_llm()
```

也就是说，`chroma_rag_planner.py` 是“带 RAG 的 planner 包装层”，`llm_planner.py` 是“真正调用 LLM 生成 workflow JSON 的核心 planner”。

具体看 `chroma_rag_planner.py`：

```python
def plan_workflow_with_chroma_rag(
    user_query: str,
    model: str | None = None,
    top_k: int = 4,
) -> dict:
    context, retrieved = retrieve_chroma_context(user_query, top_k=top_k)
    plan = plan_workflow_with_llm(
        user_query,
        model=model,
        extra_context=context,
    )
    plan["retrieved_context"] = retrieved
    plan["retriever"] = "chroma"
    return plan
```

这段代码的顺序非常清楚：

第一步：

```python
context, retrieved = retrieve_chroma_context(user_query, top_k=top_k)
```

先从 Chroma 向量库里检索相关知识，比如：

```text
QGIS 工具说明
道路长度任务指南
历史 workflow 示例
eval case
```

第二步：

```python
plan = plan_workflow_with_llm(
    user_query,
    model=model,
    extra_context=context,
)
```

再把用户问题和检索到的上下文一起交给 `llm_planner.py`。

第三步：

```python
plan["retrieved_context"] = retrieved
plan["retriever"] = "chroma"
```

把检索结果附加到 plan 里，方便 trace 记录和后续解释。

二者关系可以这样理解：

```text
plan_workflow_with_llm()
  = 基础 planner
  = 负责调用 LLM 生成 workflow JSON

plan_workflow_with_chroma_rag()
  = RAG 增强 planner
  = 先查 Chroma，再调用 plan_workflow_with_llm()
```

如果不用 RAG，流程是：

```text
用户问题 -> plan_workflow_with_llm() -> workflow JSON
```

现在使用 Chroma RAG 后，流程变成：

```text
用户问题
  -> retrieve_chroma_context()
  -> 得到相关知识 context
  -> plan_workflow_with_llm(user_query, extra_context=context)
  -> workflow JSON
```

所以 `plan_workflow_with_chroma_rag()` 并不是替代 `plan_workflow_with_llm()`，而是在它外面加了一层“先检索知识”的增强逻辑。

在完整 Agent 中，`langgraph_agent.py` 的 `planner_node()` 目前是直接写了同样的逻辑：

```python
context 来自 retrieve_node()
plan = plan_workflow_with_llm(user_query, extra_context=context)
```

也就是说：

```text
evaluate_chroma_rag_planner.py 用 plan_workflow_with_chroma_rag() 测试 planner
run_langgraph_chroma_task.py 用 LangGraph 节点拆开执行 retrieve 和 plan
```

两者本质一致，只是组织方式不同：

```text
eval 脚本：把 Chroma 检索和 LLM planner 封装在一个函数里
LangGraph Agent：把 Chroma 检索和 LLM planner 拆成 retrieve_node 和 planner_node 两个节点
```

一句话总结：

`chroma_rag_planner.py` 先运行检索，再调用 `llm_planner.py`；`plan_workflow_with_chroma_rag()` 是 RAG 外壳，`plan_workflow_with_llm()` 是真正生成 workflow JSON 的核心函数。
